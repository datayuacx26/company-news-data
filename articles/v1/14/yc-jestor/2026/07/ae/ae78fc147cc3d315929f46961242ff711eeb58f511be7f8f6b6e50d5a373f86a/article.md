# When should an internal process become a table app, and when should it become a Kanban?

In **[Jestor](https://jestor.com/?ref=blog.jestor.com)** , tables are where the data lives — the process's relational database — while the Kanban is one of the possible views built on top of that table, focused on visually tracking stages.


## The confusion between data structure and display


Anyone structuring a new process wonders whether to start by thinking about table columns or Kanban phases — and that confusion tends to produce poorly designed processes from the start.


This is more common in processes with clear progress stages, like sales or approvals, where the temptation to think about the Kanban first can leave the underlying data structure too shallow.


## How to approach a new process


1. Always start with the table, defining the necessary fields and connections.
2. Add the Kanban afterward, if the process has visual progress stages.
3. Create the Kanban with one click from the existing table.
4. Apply color conditionals, filters, and card customization without altering the table.
5. Combine the table with multiple views: Kanban, list, dashboard, as the team needs.


Element What it is When to use it


Table Relational data structure, with fields and connections The base of any process, always needed


Kanban A view built on top of the table, organized by phase Processes with visual progress stages

### Frequently Asked Questions


**Can a Kanban be created later, even if the table has existed for a while?** Yes, the Kanban can be created at any time on top of an existing table, with one click.


**Can I have more than one Kanban for the same table?** Yes, different Kanbans can be created from the same dataset, each with its own focus.


**Does every process necessarily need a Kanban?** No, processes more focused on records and lookups can work well with just the table and list views.
